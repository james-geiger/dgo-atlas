# Data governance

This repository holds our business glossary and how it is governed, written
as data against the [Data Governance Ontology](https://github.com/james-geiger/dgo)
(DGO). [DGO Atlas](https://github.com/james-geiger/dgo-atlas) validates it and
builds the site.

## Build it

```bash
uv sync
uv run dgo-atlas build
```

The site lands in `site/`; open `site/index.html`. `uv run dgo-atlas validate`
checks the data without building. CI does both on every pull request.

## What goes where

| Path | What it holds |
| --- | --- |
| `governance/**/*.yaml` | Governance data. Split it across files however you like; all files are merged. One file per term keeps each change reviewable. |
| `dgo-atlas.yaml` | Site configuration: the DGO release (`dgo_version`), title, your identifier prefix, branding. Every setting and its default is in [dgo-atlas.example.yaml](https://github.com/james-geiger/dgo-atlas/blob/main/dgo-atlas.example.yaml). |
| `content/*.md` | Pages written by hand. `content/index.md` is the landing page. |
| `.dgo-atlas/*.schema.json` | Generated by DGO Atlas for editor validation. Don't edit; commit it. |

Each governance file is a mapping of lists: `processes`, `councils`,
`people`, `organizations`, `council_roles`, `governance_roles`,
`business_glossaries`, `domains`, `subject_areas`, `glossary_terms`,
`definition_sources`, `term_creations`, `term_modifications`,
`term_deprecations` and `term_status_boundaries`. The site's
"How to read a term" page describes every field of a term.

## Changing the site's wording

- **Page headers and intro text.** `content/index.md` sets the landing page.
  A Markdown file at the path of a generated index page sets that page's
  `eyebrow`, `title` and `lede` in its front matter, and its body appears as
  intro text:
  - `content/terms/index.md` → All terms;
  - `content/directory.md` → People & organizations;
  - `content/governance.md` → How governance is organized;
  - `content/how-to-read-a-term.md` → How to read a term.
- **Everything else.** Every heading, label, button, message and state name
  has a key. `uv run dgo-atlas text` lists them all with their defaults
  (`uv run dgo-atlas text term.` for one page). Override any of them under
  `text:` in `dgo-atlas.yaml`:

  ```yaml
  text:
    term.history: Change log
    count.term.other: "{n} definitions"
  ```

  Keep any `{placeholders}` in your wording. An unknown key fails the build
  and names the closest real one.

## Authoring rules

The build enforces all of these.

- **Every object with an `id` is defined once** and referenced by that id
  everywhere else. Ids are CURIEs using a prefix from `dgo-atlas.yaml`
  (`org:clinical-trial`), except definition sources, whose id is the
  source's own IRI.
- **References must resolve** to something of the right kind: a term's
  `in_subject_area` must name a subject area, `role_of` a person,
  organization or council, and so on.
- **Quote dates:** `occurred_on: "2026-09-28"`.
- **Quote yes/no/on/off** when you mean the words: unquoted, YAML reads them
  as booleans.
- **One definition per term.** A term is `part_of` one glossary and
  `in_subject_area` one subject area; its domain follows from the subject area.
- **There is no status field.** A term's state comes from its lifecycle:
  a term creation (and later term modifications or a term deprecation) with
  the term as `has_output`, each with dated status boundaries.
- **Changing a term keeps its id.** Edit it in place and record a term
  modification.
- **Never delete a term.** Record a term deprecation, and set `replaced_by`
  if there is a successor.
- **`pref_label`** is only needed when the display form differs from `label`,
  and must differ from every alt label.
- **`responsibilities`** on a term hold who currently owns, stewards, looks
  after and advises on it.

## `type` values

Roles and status boundaries have no id; `type` says which kind each is. Write
the DGO class name, exactly as DGO spells it:

```yaml
- type: owner
  role_of: org:research-office
```

DGO Atlas reads each name as its DGO class IRI (`owner` is `dgo:DGO_00000012`),
so the site and `dgo-atlas convert` exports carry DGO's own value. The IRI is
accepted in `type` too.

| Kind of | `type` | DGO class IRI |
| --- | --- | --- |
| governance role | `owner` | `dgo:DGO_00000012` |
| governance role | `steward` | `dgo:DGO_00000013` |
| governance role | `custodian` | `dgo:DGO_00000014` |
| governance role | `subject matter expert` | `dgo:DGO_00000015` |
| council role | `chair` | `dgo:DGO_00000006` |
| council role | `security steward` | `dgo:DGO_00000007` |
| council role | `ethics steward` | `dgo:DGO_00000008` |
| council role | `documentation steward` | `dgo:DGO_00000009` |
| council role | `compliance steward` | `dgo:DGO_00000010` |
| status boundary | `drafted` | `dgo:DGO_00000024` |
| status boundary | `submitted for review` | `dgo:DGO_00000025` |
| status boundary | `approved` | `dgo:DGO_00000026` |
| status boundary | `rejected` | `dgo:DGO_00000027` |

Other spellings (`Approved`, `submitted_for_review`, `dgo:Approved`) are
rejected, with the name to use.

## How a term's state is worked out

A term appears on the site once a term creation is recorded for it, unless
that creation was rejected. Its state is then:

1. **Deprecated** if a term deprecation of it has an approved boundary.
2. Otherwise **approved** if its creation has an approved boundary, or
   **proposed** while the creation is still open.

The build lists every term it leaves out, and every link to one it drops.

Modifications never change the state. An open one shows on the term's page as
a change under review.
